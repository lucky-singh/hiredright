# Production Deployment Strategy

This document outlines the cloud-agnostic deployment architecture for **HiredRight**. By leveraging **Terraform** for infrastructure provisioning and **Kubernetes (K8s)** for container orchestration, the application remains completely portable across major cloud providers (AWS, GCP, Azure, DigitalOcean) with zero changes to the application code or deployment manifests.

---

## 1. Architecture Overview

### Infrastructure as Code (Terraform)
Terraform is used to provision the foundational hardware and managed services. While the current implementation defaults to **AWS**, the provider can be swapped easily.
- **Compute:** Managed Kubernetes Cluster (e.g., AWS EKS).
- **Database:** Managed PostgreSQL (e.g., AWS RDS) to ensure automated backups, high availability, and easy scaling.
- **Storage:** S3-compatible Object Storage (e.g., AWS S3) for resumes and static media.
- **Cache/Broker:** ElastiCache (Redis) or in-cluster Redis deployments.

### Container Orchestration (Kubernetes)
The application workload runs inside the Kubernetes cluster.
- **Frontend (`hiredright-web`):** Compiled React (Vite) application served via an ultra-lightweight Nginx container.
- **Backend API (`hiredright-api`):** Django application served via Gunicorn (WSGI) in a multi-stage Python container.
- **Worker (`hiredright-celery`):** Background task processor sharing the API container image but executing the Celery worker command.
- **Ingress:** Nginx Ingress Controller routing `www.hiredright.com` to the frontend and `api.hiredright.com` to the backend API.

## 2. File Structure Reference

The deployment configurations are organized into the following directories:

### Dockerfiles
*   `apps/api/Dockerfile.prod` - Multi-stage build for the Django API using Gunicorn.
*   `apps/web/Dockerfile.prod` - Multi-stage build compiling React and serving it via Nginx.
*   `apps/web/nginx/default.conf` - Nginx configuration for SPA routing and static asset caching.

### Kubernetes Manifests (`k8s/base/`)
These manifests are 100% cloud-agnostic.
*   `api-deployment.yaml` & `api-service.yaml` - Backend API pods and networking. (Includes `/api/v1/health/` readiness probes).
*   `web-deployment.yaml` & `web-service.yaml` - Frontend SPA pods and networking.
*   `celery-deployment.yaml` - Background worker pods.
*   `ingress.yaml` - Domain routing and TLS configuration.
*   `secrets.example.yaml` - Template for environment variables (DB URLs, API keys).

### Terraform Configurations (`terraform/aws/`)
*   `main.tf` - Provisions the AWS VPC, EKS Cluster, and RDS PostgreSQL instance.
*   `variables.tf` - Parameterizes the AWS region and deployment specifics.

### CI/CD Pipelines (`.github/workflows/`)
*   `tests.yml` - Runs the `pytest` and `vitest` suites against temporary DB containers on every PR/Push to `main`.
*   `production-deploy.yml` - Builds the `Dockerfile.prod` images via Docker Buildx and pushes them to the GitHub Container Registry (GHCR) upon a successful merge to `main`.

## 3. Deployment Workflow

1. **Infrastructure Provisioning:**
   Navigate to `terraform/aws/` and run `terraform init` and `terraform apply`. This takes ~15 minutes and yields the Kubernetes Cluster credentials and the Database connection URL.
2. **Secrets Management:**
   Use the Database URL generated by Terraform to populate your Kubernetes secrets (based on `k8s/base/secrets.example.yaml`). Apply it via `kubectl apply -f k8s/base/secrets.yaml`.
3. **Continuous Deployment (CI/CD):**
   When code is pushed to `main`, GitHub Actions automatically builds the Docker images and pushes them to `ghcr.io`.
4. **Cluster Update:**
   Apply the Kubernetes manifests using `kubectl apply -k k8s/base/`. Kubernetes will perform a rolling update, pulling the new images and gracefully swapping out the old pods with zero downtime.

## 4. Production Considerations & Best Practices

*   **Secrets Management:** Never commit `secrets.yaml` to version control. In a true enterprise environment, integrate **External Secrets Operator** (fetching from AWS Secrets Manager) or **Sealed Secrets** to manage sensitive variables.
*   **Static Files:** Ensure Django's `collectstatic` is run during the CI/CD pipeline or deployment phase. Currently, the API image expects static files to be served either via WhiteNoise or offloaded to an S3 bucket via `django-storages`.
*   **Database Migrations:** Run migrations automatically during deployment using a Kubernetes `Job` or a release phase in your CI/CD pipeline (`python manage.py migrate`), rather than running them manually.
*   **Scaling & Resource Limits:** Kubernetes `Deployment` manifests are strictly configured with CPU and Memory `requests` and `limits`. This guarantees predictable performance and protects the cluster from Node-level Out of Memory (OOM) cascading failures. It also fully enables you to deploy a **Horizontal Pod Autoscaler (HPA)** to dynamically scale based on CPU usage during high-traffic periods.
